# Assumptions and decisions

- The default `ApplicationMode` is **Assessment**, matching the PDF. It has no login, document gate or real payment. The optional authenticated Portal mode is explicitly selected and has a separate controller surface; its routes are absent in Assessment mode, and the assessment's anonymous routes are absent in Portal mode.
- Each named class/shift has its own capacity. A student may apply to multiple classes, but may have only one active hold or confirmed admission in any particular class. Expired/cancelled holds remain in history and do not block reapplication.
- The student is identified by exactly 17 ASCII digits in `X-Student-Id`. Missing or invalid identity returns 400. Public `GET /holds/{holdId}` follows the PDF contract. Confirmation/cancellation compare the supplied identity with the hold owner; the header is a local assessment identity convention, not verified authentication.
- Applying means immediate seat reservation. Admission-fee confirmation is simulated and charges no money. Repeated confirmation of the same already-confirmed application succeeds without counting a second seat. Expired/cancelled holds cannot be confirmed. A confirmed admission cannot be cancelled. Repeated cancellation of an unconfirmed hold is safe.
- Default hold duration is **600 seconds**, configurable by `HOLD_DURATION_SECONDS`. All capacity/time decisions use UTC after acquiring database locks. Hosts sharing a database should have synchronized clocks.
- First-come means the order in which competing requests acquire the PostgreSQL class-row lock. Browser click times and network arrival order cannot be guaranteed across clients. No lottery or scheduling queue is used.
- Reservations, confirmations and cancellations lock the class row in a transaction; confirmation/cancellation then lock the hold row and validate its current state and time. All API processes sharing PostgreSQL contend for the same database row lock. After acquiring it, each reservation rechecks active holds, confirmed admissions and duplicate applications, and only inserts a hold when `held + confirmed < totalSeats`. The transaction commits before releasing the lock, so the next process observes that reservation. Concurrent confirmation rechecks the locked hold and counts an already-confirmed admission only once.
- The optional `docker-compose.concurrency.yml` exposes independent APIs on ports **8080** and **8081** with the same database connection. `scripts/verify-assessment.py --exercise --secondary-api http://localhost:8081` checks 30 concurrent reservations across both processes for five seats: five requests must return 201 and 25 must return 409. Run fixture creation on a disposable database, as described in README.md. Frontend automated tests run in Docker through the `frontend-tests` test-profile service.
- Reads compute effective expiry and exclude expired holds immediately without writing stale entities back. A background worker conditionally persists expired HELD rows every five seconds without needing an admission API request. Conditional updates cannot overwrite confirmed/cancelled states.
- Explicit transactions use Npgsql's non-retrying execution strategy. A transaction-scoped retry would be required before introducing automatic retries. Uncommitted transactions roll back and release locks.
- PostgreSQL is required at runtime. Startup applies versioned migrations under a PostgreSQL advisory lock and fails if initialization fails. The initial migration can adopt the original matching core `EnsureCreated` schema without deleting its classes or admissions. This is not a general repair mechanism for arbitrary schemas.
- Student identity and selected hold persist in localStorage. Changing identity clears the selected hold and ignores pending responses for the previous student. Server history restores an active hold if local selection is absent. When browser storage is unavailable, the current session still works.
- Class counts poll every three seconds; hold status and history poll every four seconds. A one-second local countdown disables expired payment immediately. Requests have a ten-second timeout; errors are shown in the UI. Polls do not overlap within a view, so slow responses can still complete. Successful confirmation updates state from its mutation response immediately.
- Frontend API URL is compiled from `VITE_API_URL`; changing it requires rebuilding the image. Same-origin `/api` is the default. For an absolute HTTP(S) URL, the Docker build generates a CSP allowing that specific origin. Assessment CORS accepts the configured browser request without cookie authentication.
- Docker-only startup includes local assessment database defaults and does not require `.env` or external providers. Existing named volumes persist across `down`/`up`. The retained volume names preserve previously created data. No example classes, students or admissions are seeded for the assessment.
- Regression tests use disposable PostgreSQL databases. The optional two-container API setup is used for real cross-process HTTP concurrency verification. Persistence verification records a confirmed hold and checks that exact record after Compose down/up, rather than inferring persistence from a health endpoint.
