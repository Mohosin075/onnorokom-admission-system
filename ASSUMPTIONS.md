# Assumptions and decisions

- **Class and student identity:** Each class/shift has independent capacity. A student may apply to different classes, but only one active hold or confirmed admission is allowed per class. Expired/cancelled records remain in history and permit reapplication, so an unsuccessful attempt does not permanently block admission.
- **Identity boundary:** The 17-digit birth registration number is passed as `X-Student-Id`, as specified. Confirmation and cancellation check ownership. This header identifies the student for the assignment; it does not verify identity against a government registry.
- **Payment and cancellation:** Applying immediately reserves a seat; payment is simulated. Repeated confirmation returns the existing confirmation without consuming another seat. Expired/cancelled holds cannot be confirmed, and confirmed admissions cannot be cancelled, preserving the final admission.
- **First-come order:** Competing reservations are ordered by acquisition of the PostgreSQL class-row lock. Browser click times and network arrival order cannot establish a reliable global order.
- **Capacity across processes (bonus):** An initial read rejects full classes or duplicates quickly. Successful reservations acquire the class row with `FOR UPDATE` inside a transaction, then repeat capacity/duplicate checks before insertion. Confirmation/cancellation use database locks too. Independent API processes therefore coordinate through the same database, keeping `held + confirmed <= totalSeats` without an in-process mutex. The optional `concurrency` Compose profile exposes APIs on ports 8080 and 8081; CI checks competing requests across both.
- **Expiry and time:** Holds default to 600 seconds through `HOLD_DURATION_SECONDS`. Server UTC determines expiry; hosts sharing the database must have synchronized clocks. Availability excludes overdue holds immediately, while a worker persists their expired status every five seconds without an admission API call. Payment is disabled at the deadline.
- **Connection budget:** Pools default to 40 connections per API process; explicit connection-string limits take precedence. Two APIs therefore budget 80 connections against PostgreSQL's default 100. More processes require adjusting the shared budget.
- **Browser recovery:** Student identity and selected application are saved in localStorage; server history restores applications after refresh or reopening. Class counts poll every three seconds and applications every four seconds, keeping views current without page reloads.
- **Startup and persistence:** Default Assessment mode requires no login or external payment/email service. No sample admissions or classes are seeded. Named Docker volumes preserve data across `down`/`up`; `down --volumes` intentionally deletes it. Automated integration tests use disposable databases to protect application data.
